Bug Bounty · Finding 01

Carenium Healthcare Platform — Insecure Direct Data Disclosure (Anonymous KYC/Photo Exfiltration)

Critical · CVSS 9.1 Vulnerability Disclosure Client-Assisted PT Vendor: Carenium

Researcher: Abdulkadar  ·  Date: 2026-09-13  ·  CVSS 3.1: 9.1 — Confidentiality (AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N)

1 · Executive Summary

A client-assisted security assessment of the Carenium healthcare platform identified a Critical information-disclosure chain. The production web app embeds its Supabase anonymous (anon) API key in publicly served JavaScript bundles. That key grants unauthenticated read access to the profiles table via Supabase's PostgREST API, exposing the complete PII of registered users: passport photographs, Google profile avatars, full home street addresses, mobile numbers, email addresses, Aadhaar numbers, PAN numbers, membership card numbers, and health-related columns (allergies, chronic conditions, blood group), plus subscription and KYC metadata. An additional public storage bucket (carenium-card-photos) exposed passport images fetched without any authentication.

The exposure required no account, no credentials, and no session. It was reproduced end-to-end and all artifacts were preserved for disclosure.

2 · Scope & Authorization

  • Engaged under a client relationship with the target organization (authorized penetration testing / vulnerability assessment).
  • Target: www.carenium.in + associated Supabase backend.
  • Constraint followed: no destructive testing, no DoS, no mass data exfiltration beyond proof-of-concept confirmation; any test records created were minimal and reversible.

3 · Methodology

  1. Recon — Host enumeration: carenium.in (Vercel, 308 → www), carenium.com (dead/OVH placeholder). Stack identification via HTTP headers and HTML fingerprints → Next.js on Vercel.
  2. Client-side analysis — Downloaded the app's _next/static/chunks/*.js bundles and grepped for endpoints/keys. Found the Supabase project URL and anon JWT; app used .from("profiles").
  3. API discovery — Probed Supabase REST (/rest/v1/<table>), GraphQL (/graphql/v1), edge functions (/functions/v1/<fn>), and storage (/storage/v1/bucket, /object/list).
  4. Data validation — Confirmed user data disclosure, enumerated sensitive columns, counted populated rows, decoded embedded base64 images, and verified public-bucket objects were downloadable anonymously.
  5. Write-path tests — Attempted INSERT/UPDATE/object upload to confirm scope is read-only (all denied by RLS — good).

4 · Findings

4.1 CRITICAL — Anonymous disclosure of user passport photos & KYC data

  • Endpoint: POST /rest/v1/profiles?select=* with apikey: <anon>
  • Root cause: anon key shipped in public JS bundle + permissive RLS policy allowing anonymous select on profiles + sensitive documents stored as base64 inside a DB column.
  • Live impact (at assessment time): passport_photo_url populated for 9 users (8 as embedded data:image/webp base64, 1 in public storage) — full passport images recoverable to disk; avatar_url 25; aadhar_number 10; pan_number 6; email 38/38; phone 20; mobile 16; carenium_card_number 10; subscription data several.
  • Sample evidence: profiles?select=id,full_name,passport_photo_url returned valid WebP base64 (decoded & verified), and a public-bucket passport JPEG (413KB, with EXIF device + timestamp metadata).

4.2 HIGH — Full street addresses & phone numbers of real users

  • Same profiles table returned complete postal addresses and contact numbers (address/address_line populated for 17 and 10 rows). Cross-referenceable with names, photos, and emails — a complete identity dossier per user.

4.3 MEDIUM — Public storage bucket

  • carenium-card-photos is a public bucket (listable + readable anonymously) containing passport images, one with sensitive EXIF (device model + timestamp).

4.4 LOW / INFORMATIONAL — Additional attack-surface observations

  • Open self-signup (POST /auth/v1/signup) returns an authenticated JWT — no RLS escalation possible (other tables scoped to auth.uid()) — noted for defense-in-depth.
  • profiles.cloud_app_state contains a GPS location schema (latitude/longitude/accuracy). Values null at assessment time, but the schema sits inside an already-readable table → forward privacy risk (would become a live-tracking leak).

4.5 Verified NOT vulnerable (negative results — good posture)

  • INSERT/UPDATE on profiles and other tables: RLS-denied.
  • Upload into storage bucket: RLS-denied (403 AccessDenied).
  • payments, orders, cashfree_orders, carenium_cards, health_records, family_members, hospitals, prescriptions, doctor_profiles, appointments: all RLS-scoped to auth.uid() — no cross-tenant read.
  • No service_role keys, GraphQL, or edge functions exposed.

5 · Proof of Concept (redacted)

# 3-step chain — no credentials required

# 1. anon key recovered from the app's JS bundles (grep)
grep -rhoE 'eyJ[A-Za-z0-9_-]{20,}\.[A-Za-z0-9_-]{20,}\.[A-Za-z0-9_-]{20,}' _next/static/chunks/*.js

# 2. enumerate users + passport photos
curl -s "https://<proj>.supabase.co/rest/v1/profiles?select=id,full_name,aadhar_number,pan_number,phone,mobile,email,address,address_line,carenium_card_number,passport_photo_url&passport_photo_url=not.is.null" \
  -H "apikey: <anon>" -H "Authorization: Bearer <anon>"

# 3. passport image exfiltration (embedded base64 or public-bucket URL)

Actual sensitive values (PII) intentionally excluded from this public write-up.

6 · Impact

  • Identity fraud: passport photo + Aadhaar + PAN + full address + phone in one payload per victim — every component needed to open accounts, apply for loans, or bypass KYC elsewhere.
  • Physical / social-engineering risk: home addresses + phone numbers + photos of a healthcare user base.
  • Health-data privacy: medical fields (allergies, chronic conditions, blood group) exposed in violation of healthcare-data expectations.
  • Reputational/regulatory exposure for a healthcare brand (India: DPDP Act 2023 relevant).

7 · Remediation (recommended)

  1. Move all data access behind a server-side API; remove the anon key from client bundles (and disable client-side direct DB access).
  2. Restrict RLS on profiles: anon may not select PII columns; narrow to auth.uid() = id, and mask sensitive fields.
  3. Make storage private; serve via short-lived signed URLs. Stop storing base64 images in-table.
  4. Scope-down cloud_app_state (remove GPS schema from readable surface).
  5. Add anonymous-read rate/volume alerting on profiles.

8 · Timeline / Disclosure

  • 2026-09-13 — Assessment performed; findings confirmed and documented.
  • Initial disclosure to client with remediation guidance; fix verification in progress.
Bug Bounty · Finding 02

Unauthenticated Orthanc PACS Admin API Exposes Patient Medical Data (PHI) on zfp-direct.dekco.ai

Critical · Severity Not Confirmed CWE-285 Improper Authorization Report #73328074 Scope: pacs.dekco.ai

Report Summary

The Dekco imaging viewer (zfp-direct.dekco.ai) proxies an Orthanc DICOM server whose full admin REST API (/orthanc/*) is publicly reachable with NO authentication. Confirmed via /orthanc/system (IsHttpServerSecure: false, ReadOnly: false). Any attacker on the internet can enumerate and download real patients' demographics and raw medical images (DICOM), and — because the server is not read-only — can modify/delete studies and inject data. Verified with two independent real patients.

Vulnerability Impact

Unauthenticated internet access to the PACS admin API leaks real patients' demographics + medical images (PHI) and allows modification/deletion (ReadOnly: false) — a Critical healthcare data breach.

Proof of Concept

The Dekco imaging viewer host zfp-direct.dekco.ai reverse-proxies an Orthanc DICOM/PACS server whose entire admin REST API (/orthanc/*) is publicly reachable with no authentication. Confirmed via /orthanc/system returning "IsHttpServerSecure": false and "ReadOnly": false.

Any unauthenticated internet user can enumerate resource IDs (/orthanc/changes), view real patient demographics and study metadata with PHI, download whole-study ZIP archives, and download raw DICOM medical images. Because the instance is not read-only, an attacker can also modify, delete, anonymize, or inject imaging studies, and abuse DICOM modalities/peers (C-MOVE) to probe internal infrastructure (SSRF). This is a Critical healthcare data breach affecting regulated patient health information.

Security Impact

  • Confidentiality (critical): mass exposure of real patients' PHI (name, ID, date of birth, sex, institution, referring physician, study details) and the medical images themselves, from anywhere on the internet with zero credentials.
  • Integrity (high): ReadOnly: false permits bulk-delete, modify, anonymize, and create-dicom — an attacker can alter or destroy medical records and inject fake studies.
  • Availability: bulk deletion or resource exhaustion can take down imaging data access.
  • Network pivot / SSRF: DICOM storage/retrieve (modalities, peers, C-MOVE) can be aimed at internal hosts.
  • Regulatory: exposure of real-patient health data (India DPDP Act / global equivalent). Verified on two independent patients.

Steps To Reproduce

No pre-conditions required — no login, no session, no cookies. Direct unauthenticated requests:

  1. Confirm the API is open and writable: 
    curl "https://zfp-direct.dekco.ai/orthanc/system"
# 200 OK → "IsHttpServerSecure": false, "ReadOnly": false, "Version": "1.12.7"
  2. Retrieve a real patient's study metadata (PHI) — 200 OK, PatientMainDicomTags populated (name, patient ID, birth date, sex; study e.g. "LT SHOULDER" at a sports-med facility). Patient details redacted here for privacy.
  3. Second independent patient — proves systemic exposure (study e.g. "knee^NM" at a 3T MRI center). Details redacted.
  4. Download the full study (ZIP) and a raw DICOM image without auth: 
    curl -o study.zip "https://zfp-direct.dekco.ai/orthanc/studies/[id]/archive"
curl -o img.dcm "https://zfp-direct.dekco.ai/orthanc/instances/[id]/file"
file study.zip   # => Zip archive data
file img.dcm     # => DICOM medical imaging data
  5. Enumeration proof — the changes feed lists every resource ID: 
    curl "https://zfp-direct.dekco.ai/orthanc/changes" | jq -r '.Changes[] | "(.ResourceType)\t(.ID)"'

Specifics

  • Account used: none required — the endpoint is unauthenticated.
  • Domains affected: zfp-direct.dekco.ai — Orthanc/DICOM backend that serves the production platform pacs.dekco.ai (referenced by its CSP frame-src).
  • Versions/vendors: Orthanc 1.12.7 (DICOM AE ORTHANC, HTTP port 8042; PostgreSQL index plugin + S3 storage plugin). Exposed via Cloudflare.

Recommendations

  1. Enable authentication on Orthanc — create RegisteredUsers and disable anonymous access to the REST API.
  2. Put /orthanc/* behind an authenticated reverse proxy/WAF allowlisted to only the trusted viewer origin.
  3. Set ReadOnly: true for the exposed front-end path so any API exposure cannot modify or delete data.
  4. Remove admin endpoints from public reach — /orthanc/system, /tools, /changes, /peers, /modalities should never be externally accessible.
  5. Treat as a breach — audit /orthanc/changes history for prior unauthorized access, rotate any DICOM/storage credentials, and follow applicable legal notification obligations for the PHI involved.
  6. Verify the fix — unauthenticated requests to https://zfp-direct.dekco.ai/orthanc/* must return 401/403.
Bug Bounty · Finding 03

Unauthenticated SQL Injection and Database Write via POST /api/dpu/aliases

High · Severity Not Confirmed CWE-89 SQL Injection Report #80036429 Scope: vibinex.com

Report Summary

The POST /api/dpu/aliases endpoint appears to be vulnerable to SQL injection due to the construction of an unparameterized SQL UPDATE statement using attacker-controlled values, including repo_name, repo_owner, repo_provider, and aliases.

The endpoint is also accessible without authentication, allowing an unauthenticated attacker to submit crafted input directly to the affected database operation.

During testing, supplying a single quote (') produced a measurable difference in behavior, including a confirmed HTTP 200 vs. HTTP 500 response differential — demonstrating attacker-controlled input reaches the SQL query without being safely parameterized or escaped. Further testing demonstrated a boolean/error-based SQL injection oracle that can potentially infer data from the underlying database, which may expose sensitive records including user account information and OAuth-related data stored in auth_info.

Vulnerability Impact

Unauthenticated SQL injection, no session required; attacker input executes as SQL on the DB (proven by 200/500 differential). Enables tampering with repos.aliases to poison reviewer-relevance data and arbitrary DB writes/reads, including users and stored OAuth tokens.

Proof of Concept

The DPU alias endpoint POST https://vibinex.com/api/dpu/aliases executes an unparameterized SQL UPDATE on the repos table using fully attacker-controlled input (repo_name, repo_owner, repo_provider, aliases) with no authentication whatsoever (unlike other /api/* handlers, it never calls getServerSession). In source (pages/api/dpu/aliases.ts → utils/db/aliases.ts:14-24) the values are string-concatenated into the query.

Black-box confirmation on the live service: a benign request returns 200 OK; a single quote in the aliases value causes a database error 500 — proving unauthenticated attacker input is being executed as SQL. A single quote in either aliases or repo_name independently breaks the query (confirmed 500 vs 200 baseline). Multiple attack-controlled fields reach the SQL statement unparameterized.

Security Impact

An unauthenticated, internet-facing attacker can:

  • Execute arbitrary SQL against the application database (confirmed via 200/500 differential).
  • Tamper with repos.aliases data for any onboarded repository — this data drives reviewer-assignment relevance and PR comment generation, so injected aliases poison the product's core review logic (false contributor/reviewer attribution, junk "missing profile handles" comments).
  • Read the aliases/identity mapping for any repo via the corresponding unauthenticated GET (git emails → provider handles), enabling team/account enumeration.

Steps To Reproduce

No account, session cookie, Authorization header, or any authentication is required. Tested with plain curl against the production service.

  1. Baseline — benign POST (expected 200 OK): 
    curl -si https://vibinex.com/api/dpu/aliases -X POST -H 'Content-Type: application/json' \
  --data '{"repo_name":"repo","repo_owner":"owner","repo_provider":"github","aliases":["a@b.c"]}'
# HTTP/2 200 → OK
  2. Injection trigger — single quote (JSON escape \u0027) in the aliases value (expected 500): 
    curl -si https://vibinex.com/api/dpu/aliases -X POST -H 'Content-Type: application/json' \
  --data '{"repo_name":"repo","repo_owner":"owner","repo_provider":"github","aliases":["x\u0027"]}'
# HTTP/2 500 → {"error":"Unable to save aliases to DB"}
    The error is raised by PostgreSQL when the quote breaks the string literal, i.e. the attacker string is evaluated as SQL.
  3. Quote in repo_name instead (also 500): 
    --data-raw '{"repo_name":"x\u0027","repo_owner":"o","repo_provider":"github","aliases":["a@b.c"]}'
# HTTP/2 500 → same DB-error body — confirms a second injectable field.

Specifics

  • Account used: None — fully unauthenticated; no session/cookies/credentials required.
  • Domain affected: vibinex.com — endpoint POST /api/dpu/aliases.
  • Version: Not version-specific. Tested against the Vercel-hosted production deployment. Related public source: github.com/Alokit-Innovations/vibinex-server (pages/api/dpu/aliases.ts, utils/db/aliases.ts:14-24).

Recommendations

  1. Convert utils/db/aliases.ts queries to parameterized statements ($1, $2, ...) — never concatenate user input into SQL.
  2. Add authentication/authorization to all /api/dpu/* endpoints (server-side session check or a shared secret/bearer token used only by the DPU), matching the existing pattern on other /api/* handlers.
  3. Strictly validate repo_owner, repo_name, repo_provider, and each alias value (e.g., email regex whitelist).
  4. Restrict DPU endpoints so they can only be reached by the trusted DPU service layer.
  5. Harden DB credentials used by the application tier and review storage of OAuth tokens in auth_info.
